Part 1

How the web works

You type an address, press Enter, and about a second later a page appears. In that second your laptop finds another computer somewhere in the world, asks it for files, gets them back, and turns them into the pixels you see.

Part 1 follows that trip one step at a time. Press play to see the whole trip first.

  1. You type a URLThe address of the page
  2. DNS finds the IPThe name becomes a number
  3. The browser asksAn HTTP request goes out
  4. The server answersFiles come back with a status code
  5. The browser buildsText becomes a tree, then boxes
  6. You see the pagePixels on your screen

Each box links to the section that explains it.

1.1

Two computers talking

Where does a website actually live? Not inside your browser. It lives as ordinary files on another computer, and your browser asks that computer for a copy every time you visit.

The computer that asks is the client. On your laptop, the client is the browser, Chrome. The computer that answers is the server. A server is a normal computer, usually without a screen, kept switched on all day and waiting for requests. GitHub runs thousands of them.

Think of it like a restaurant

  • You are the client. You don't walk into the kitchen. You place an order.
  • The kitchen is the server. It has everything ready and sends out what you asked for.
  • Your order is the request. The plate that comes back is the response.
  • The waiter carrying both ways is the internet.

How the message travels

Your laptop and the server are not joined by one long wire. Between them sit many routers, small computers that pass data along like a relay team. Your Wi-Fi box is the first one.

Big messages don't travel in one piece either. They are cut into small numbered packets. Each packet can take a different road, so they often arrive out of order. The receiver puts them back in order using the numbers, and asks again for any packet that went missing.

Demo

Your laptop sends "HELLO VASAVI" to a server, cut into 4 packets. Send it a few times. The packets race differently each time.

The server's inbox is empty.

Quick check

You open Instagram on your phone. Which one is the client?

  1. Those are the servers. They hold the photos and answer requests.

  2. The client is whatever sends the request. Here, that's the app on your phone.

  3. The router only passes messages along. It never asks for anything itself.

Quick check

A photo is cut into 300 packets. Packet 120 arrives before packet 7. What happens?

  1. The packets are numbered, so the order they arrive in doesn't matter.

  2. The numbers fix the order, and a missing packet gets asked for again.

  3. Only a missing packet is sent again, not the whole photo.

Say it in an interview

A website is a set of files on a server. My browser is the client. It sends a request, and the server sends back a response. On the way, the data is cut into small numbered packets that pass through routers and get put back together at the end.

1.2

Reading a URL

https://vasavi.github.io/dice-roll/index.html looks like one long word. It is really several small pieces, and each piece has a different job.

URL stands for Uniform Resource Locator. It is the full address of one file on the internet. Paste any address below, or pick an example, and the demo splits it into its parts.

Demo

URL splitter

Edit the address and watch the parts change. Try deleting #history, or adding ?player=2 before it.

Watch outURLs can't contain spaces. A space in a folder name becomes %20, so Dice Roll/index.html turns into Dice%20Roll/index.html. That's why web file names use dashes instead, like dice-roll.

Quick check

In https://shop.com/cart?item=pen#reviews, which part never travels to the server?

  1. The domain is needed first of all, to find the server.

  2. The server needs the path to know which page to send.

  3. The query is sent. The server reads it to know which item you mean.

  4. The browser keeps the fragment to itself and scrolls to the element with id="reviews".

Quick check

What is the path in https://github.com/vasavi/dice-roll?

  1. That's the host, the name of the server.

  2. Everything after the host, up to a ? or #, is the path.

  3. That's the scheme. It says how to talk to the server.

Say it in an interview

A URL is the address of a file on the web. It has a scheme like https, a host like github.com that DNS turns into an IP address, an optional port, and a path to the file. It can end with a query after the question mark and a fragment after the hash. The fragment never goes to the server. The browser uses it to jump to an element with that id.

1.3

IP addresses and DNS

Computers don't understand names like github.com. They find each other by number. So who turns the name into a number?

Every device on the internet has an IP address. The common kind, IPv4, is four numbers from 0 to 255 joined by dots, like 185.199.108.153. That allows about 4.3 billion addresses, and the world ran out of them years ago. So there is also IPv6, which is much longer, like 2606:50c0:8000::153.

One address is worth remembering. 127.0.0.1, also called localhost, always means "this computer". You'll meet it again in 1.7.

Nobody wants to remember 185.199.108.153. DNS, the Domain Name System, is the internet's contact list. You give it a name, and it gives back the number.

Think of it like your phone's contacts

You tap "Amma" and your phone dials the number saved behind that name. You never type the number yourself. DNS does the same for websites. You type github.com, DNS finds the number, and the browser connects to that number.

Who knows the answer?

No single computer knows every name. A lookup is a chain of questions, and most servers in the chain only know who to ask next. Step through it below.

Quick check

You type 185.199.108.153 straight into the address bar instead of a name. Is a DNS lookup needed?

  1. DNS only turns names into numbers. You already gave it the number.

  2. DNS exists only because people prefer names to numbers.

Quick check

Why does a website you visited yesterday often open faster today?

  1. That's luck. There's a reason that works every time.

  2. Chrome saved the DNS answer, and often the files too, so it skips part of the trip.

  3. Servers don't speed up for you. Your own laptop does the remembering.

Say it in an interview

Computers find each other by IP address, like 185.199.108.153. DNS turns a domain name into that IP address. The browser checks its cache first, then asks a resolver. The resolver asks a root server, then the server for the ending, like .io, then the domain's own name server, which gives the answer. Each step caches the answer, so the next visit is faster.

1.4

HTTP: the request and the response

Now the browser knows the server's number. What does it actually say to it?

Browser and server talk in HTTP, the HyperText Transfer Protocol. A protocol is a set of rules both sides agree on, the way every phone call starts with "Hello?". An HTTP message is plain text with a fixed shape. Here is the browser asking for your CSS file, and the server's reply.

Request, from the browser

GET /dice-roll/style.css HTTP/1.1Start line: method, path, version
Host: vasavi.github.io
Accept: text/cssHeaders: extra details, one per line
Blank line: the headers are over

Response, from the server

HTTP/1.1 200 OKStart line: version, status code, message
Content-Type: text/css
Content-Length: 980Headers: what's coming, and how big
Blank line
body { font-family: Arial, sans-serif; ...Body: the file itself

The first word of a request is the method. It says what the browser wants to do.

MethodMeansUsed for
GETGive me thisPages, CSS, JS, images. Almost every request your project makes.
POSTTake thisSending data, like a login form or a new comment.
PUT / PATCHUpdate thisChanging something already saved, like editing your profile.
DELETERemove thisDeleting something, like a post.

One page, many requests

A page is rarely one file. The browser first gets the HTML, reads it, and finds the <link>, <script> and <img> tags. Each one starts a new request. Your Dice Roll page needs four. The demo copies the Network tab in Chrome's DevTools, the panel you open with F12.

Each file needs its own request, so the browser gets the HTML first and then asks for the CSS, JS and images it links to.

      

    


    
    

      
1.5

      
HTTPS and the lock

      
HTTP messages are plain text. On the way to the server they pass through the café's Wi-Fi and a string of routers. Who else can read them?

      
With plain HTTP, anyone on the path can read every message. It's a postcard, and every postman can read a postcard. They could even change what it says. HTTPS fixes this. It's the same HTTP, sent through an encrypted connection called TLS. Only your browser and the server can unlock it.

What HTTPS promises

      
    
        
  • Private. Nobody on the way can read the messages.
    • 
        
  • Unchanged. If someone alters a message on the way, the browser notices and rejects it.
    • 
        
  • The real server. The site shows a certificate, a digital ID card signed by a trusted company called a Certificate Authority. Your browser checks it before trusting the server.
    • 
      


      
The handshake, simplified

      
Before any page is sent, the browser and server set up the secure connection. It takes a few milliseconds.

      
    
        
  1. Browser: Hello. These are the kinds of encryption I can use.
    2. 
        
  2. Server: Hello. Let's use this one. Here is my certificate.
    3. 
        
  3. Browser checks the certificate. Is it signed by an authority I trust? Is it for this exact domain? Has it expired?
    4. 
        
  4. Both sides work out a shared secret key without ever sending the key itself. Every message after this is locked with it.
    5. 
      


      
What your address bar shows

      

        
Not securehttp://example.com

        
https://github.com

      

      
Plain HTTP pages get a Not secure label. In 2023 Chrome replaced its old padlock with the small sliders icon, because many people thought the lock meant "this site is safe". Firefox still shows a padlock. Click the icon and choose "Connection is secure" to see the certificate.

      
HTTP uses port 80 and HTTPS uses port 443, which is why you never type them. GitHub Pages gives every github.io site HTTPS for free, so your Dice Roll link will start with https:// without you doing anything.


      
Watch outHTTPS doesn't mean a site is honest. A scam site can get a certificate too. HTTPS only promises that the connection is private and that you're really talking to that domain. So always read the domain. github.com and github-login-help.com have different owners.

HTTPS is HTTP sent through an encrypted TLS connection. Nobody on the way can read or change the messages, and the server's certificate proves it owns the domain.       When JavaScript changes something later, the browser repeats only the steps it needs. Your Roll button changes an image's src and the text in #result. A new colour only needs a fresh paint. A change in size needs layout and paint again.
      

      
      Why <script> goes at the end of <body>
      
      
      The browser builds the DOM from top to bottom. When it meets a <script> tag, it stops, downloads the JavaScript, runs it, and only then carries on. If your script sat in the <head>, it would run before the buttons exist, and document.getElementById("btn1") would return null. At the end of <body>, every element above it is already in the DOM.
      
      
      You may see <script defer> in other projects. It's another way to get the same result. Your end-of-body way is fine.

      Say it in an interview

Then layout works out each box's size and position, and paint fills in the pixels. A script pauses the parser while it runs, so I put mine at the end of the body, after the elements it uses.

        • 
          
      • Use forward slashes / in paths, not Windows backslashes.
        •
